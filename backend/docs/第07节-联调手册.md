## 3. 验证步骤与断言

1. 检查现有 8000 服务及接口；使用项目 `.venv/bin/python` 启动独立 `mcp_server.py`，等待真实 MCP `initialize`、`tools/list` 完成。
2. 通过 JSON 登录接口登录 admin、aaa、bbb，检查管理员/学生角色及两个学生不同的用户 ID。
3. 使用管理员的 `POST /api/course` 新增一门唯一编码 `E2E07-<随机标记>` 的临时课程；通过 **`POST /api/schedules`** 给 aaa 新增两条不同日期的课表、给 bbb 新增一条课表。
4. 使用 aaa 的 Token 调用 `GET /api/mcp/my-schedule`。断言其包含本次 aaa 的两条记录，不包含 bbb 的记录；`course_name` 与课程列表接口返回的名称一致；完整结果与 aaa 通过业务接口查询的本人课表一致。
5. 使用 `?date=2026-10-10` 验证日期命中；另选择 aaa 当前没有课表的合法日期验证不命中，结果为 `items=[]`、`count=0`。已有数据不会干扰临时记录的识别或不命中日期的选择。
6. 使用 `?date=2026-13-99`，断言返回业务错误、`data=null`，提示包含 `YYYY-MM-DD`。当前接口约定为 **HTTP 200、JSON 中业务码非 200**，不能仅凭 HTTP 200 判断此请求成功。
7. 不携带 Token 和携带用错误密钥签名的伪造 JWT 时，断言均为 **HTTP 401、业务码 401**。
8. 换成 bbb 的真实 Token，断言只能看到本次 bbb 的临时记录，看不到 aaa 的任何临时记录；完整结果与 bbb 通过业务接口查询的本人课表一致。
9. `finally` 使用业务 DELETE 接口先删除本次课表、再删除本次课程，并通过 GET 回查确认清理。它只处理唯一标记对应的数据；原有课程、课表、账号和学习计划不被删除。随后终止并回收它启动的 MCP 进程，确认 8001 释放。

每次运行产生不同的课程编码，既不依赖数据库为空，也不要求固定课程 ID。数据库时间字段由业务接口及 ORM 正常填写，无需 SQL 补时间。

如果运行中发生断言失败或按 Ctrl+C，仍进入清理流程，并以非零退出码结束。若 FastAPI/数据库在清理阶段不可用，脚本会明确报告清理失败和本次唯一标记，不会报告成功；需恢复服务后核查该标记对应的临时记录。MCP 关闭位于独立的 `finally` 中，即使数据清理失败也会执行。

| 用户表 | `users` | 不是 `user`；用户 ID 从真实登录响应的 `data.user.id` 获取，不写死 ID。 |
