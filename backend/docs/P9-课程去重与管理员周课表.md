# P9 课程去重与管理员周课表

本轮处理重名课程和管理员周视图两处缺陷。课程合并只变更 `schedules.course_id` 引用，不删除课表、不改日期、教师、节次或周次范围；周接口新增管理员身份选择，学生隔离规则保留。`.env`、`schedules` 表结构、RAG 相似度阈值及四份演示资料均不在修改范围。

本文课程合并输出、508 条课表及两张“数据结构”卡片的网格属于 P9 历史验收记录。P10 已按学生独立重造课表，并把历史别名折叠为每人每 `course_id` 一个固定格；P9 的课程合并结果、管理员接口及学生防越权规则保持。文末同名截图文件已覆盖为 P10 当前界面，截图时间、数据版本及当前网格请查 [P10 验收说明](P10-演示数据隔离与截图验收.md)，不要以本文历史网格解释新截图。

## 基线与合并规则

本次修复前已复现：`users 3 / coruses 23 / schedules 508 / documents 4 / study_plans 0`。aaa 与 bbb 各有 254 条课表。

| 名称 | 课程 ID | 编码 | 课表引用 |
| --- | --- | --- | --- |
| 数据结构 | 2 | DS101 | 10 条 |
| 数据结构 | 50 | CS201 | 38 条 |

合并脚本 `scripts/merge_duplicate_courses.py` 按数据库的课程名称比较规则查找所有重名组，并按 ID 排序保留最小的一条。本次保留 ID=2，将 ID=50 的 38 条引用改指 ID=2，随后删除课程 ID=50。最终是 22 门唯一课程、508 条原课表，aaa / bbb 仍各 254 条。

原来两个“数据结构”授课时段均保留，这是不删除任何课表行的约束所要求的结果。第 3、6 周仍可出现两个授课格子，但都属于同一个 `course_id=2`，前端稳定哈希因此显示同一颜色。本轮没有把其中一个授课时段删掉，也没有重新安排日期。

## 数据修复命令与备份

在 `backend` 目录运行，只读检查先于修改：

```bash
.venv/bin/python scripts/merge_duplicate_courses.py --check
.venv/bin/python scripts/merge_duplicate_courses.py
.venv/bin/python scripts/merge_duplicate_courses.py --check
.venv/bin/python scripts/merge_duplicate_courses.py
```

`--check` 只报告重名组、保留项、待删项及受影响课表 ID，不修改数据库、不创建备份。第二次修改运行输出“无重复课程”，不重复改引用。

正式修改在独立会话的单一事务中完成，先锁定和核对数据，先改外键引用再删除父课程。任意错误整体回滚，退出码为 1；成功退出码为 0。事务内回查全部课表，除预期的 `course_id` 变化外，ID、日期、时间戳和其余字段必须逐项一致，否则不提交。

删除课程前，脚本把保留课程、将被删除的课程完整行、受影响课表完整行和课表 ID 写入 `backend/backups/course_merges/*.json`。文件采用排他创建、权限 0600，并完成落盘后才执行数据库修改；备份失败时不做合并。此目录已加入 `.gitignore`，不会提交真实课表备份。可用 `--backup-dir <本机目录>` 指定其他位置。

备份供人工核对和恢复使用。若已提交后确需恢复，应在数据库事务中先恢复原课程行及 ID，再按备份中的课表 ID 恢复原 `course_id`，最后核对数量与日期分布；不要先恢复指向不存在课程的外键。不要通过重新运行种子清理原课表来模拟回滚。

## 防止再次插入重名课程

`tests/manual/seed_demo_schedules.py` 的 `ensure_courses()` 现在按编码或名称任一匹配即复用已有课程。历史 CS201 / DS101 编码对应两份固定授课安排，两者共用课程 ID=2；模板编码仍用于稳定随机排课，不再要求数据库保留两条同名课程。

合并后运行既有同步命令，验证幂等性与 20 周覆盖：

```bash
.venv/bin/python tests/manual/seed_demo_schedules.py
```

本次不使用 `--clean` 或 `--reseed`，不删除 508 条课表。脚本识别 22 门唯一课程、23 个历史模板授课安排，复跑不创建新重名课程、不重排原记录。

课程新增和更新在 `app/services/course_service.py` 检查名称，比较前沿用现有去除首尾空格的规则。更新排除当前课程自身，改成原名称仍允许；与其他课程重名则拒绝。

| 触发方式 | 预期业务码 | 消息 |
| --- | --- | --- |
| `POST /api/course` 使用已有课程名称 | 409 | 课程名称已存在 |
| `PUT /api/course/{id}` 改成另一课程的名称 | 409 | 课程名称已存在 |
| 更新为自身原名称 | 200 | 请求成功 |
| 课程编码重复 | 409 | 课程编码已存在，沿用既有规则 |

`coruses.name` 仍为 `varchar(50)`，足够存储现有中文课程名。本轮未加数据库唯一索引或修改表结构，名称唯一性由业务新增/更新入口和种子同步保证；直接绕过这些入口写 SQL 的并发插入不由业务检查替代数据库约束。P5 删除关联检查保留。

## 管理员与学生的周接口

```http
GET /api/schedules/week?week=6&user_id=2
Authorization: Bearer <当前登录账号的 JWT>
```

| 调用身份 | `user_id` 参数 | 查询对象 |
| --- | --- | --- |
| 学生 | 省略或传任何值 | 永远只查 JWT 对应本人 |
| 管理员 | 省略 | 只查管理员自己；不是全校课表 |
| 管理员 | 指定存在的学生 ID | 查该学生 |
| 管理员 | 指定不存在的学生 ID | 业务 404，返回明确提示 |

`data` 顶层新增 `user_id`、`username`、`name`，始终描述被查询账号。课程行的 `user_id` 必须与顶层一致。日期范围、四档节次、七天网格、周次范围、节假日跳过和调休上课均沿用 P8 契约。未登录/伪造 JWT 仍在查询前返回 HTTP 401 与业务 401；周次越界或非整数仍为业务 400。

管理员周接口只扩展身份选择，不修改既有 `GET /api/schedules` 列表行为。业务错误继续沿用项目的 JSON 业务码包装，不把数据库异常当作 404/409 的出口。

## 前端管理员入口

管理员与学生均通过“周课表”菜单访问 `/manager/schedule-week`。管理员页面显示学生选择入口；学生不显示该控件。页面依据接口 `user_id` / `username` / `name` 明示“正在查看谁的课表”，不会把所选学生的课表标为管理员本人的课表。

选择学生时使用新的查询身份，周缓存与在途请求按学生隔离；切换学生或快速翻周时，旧请求不能覆盖新的身份和周次。四档节次、方向键翻周、假期提示、窄屏横向滚动和原列表页面保留。课程卡片仍按 `course_id` 配色，合并后的“数据结构”不再出现两种颜色。
